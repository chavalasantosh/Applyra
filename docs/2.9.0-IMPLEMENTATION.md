# Applyra 2.9.0 preview: implementation and release notes

This ZIP contains the updated Chrome extension and backend source. It is not a deployed SaaS release. Reload the unpacked extension to use the changes. No live application or payment has been submitted during development.

## Resume and profile intelligence

Open **Resume & Profile Analysis** from the workspace navigation or popup. Select the candidate, upload PDF/DOCX/TXT/Markdown, review extracted text and save it. Add Naukri and LinkedIn text snapshots and confirm experience/location. Analyze all saved jobs and pasted job descriptions together. Only loaded jobs are analyzed; descriptions absent from storage remain unknown.

The page compares job requirements with four evidence sources: stored profile, uploaded resume, Naukri snapshot and LinkedIn snapshot. It distinguishes skills absent from all evidence from profile-supported skills missing from the resume. Recommendations cover section headings, contact details, measurable achievements, portfolio links, profile completeness and recurring job requirements. Suggested achievement templates use placeholders instead of invented accomplishments.

The dashboard uses the screenshot's three-card pattern: application fit, experience fit and location fit. Counts reflect dated applications in the last seven days and show assessed denominators. Scores are keyword coverage, not ATS certification or a predicted shortlist probability. Target role preferences alone do not count as proof of a skill. Extraction requires review; scanned PDFs need OCR or pasted text. Resume bytes are not uploaded to a server by this page; reviewed text is saved in the local candidate workspace. PDF/DOCX browser parsing still needs manual acceptance testing.

## Auto Apply

The recommended-jobs bridge now clicks the actual Apply element instead of a boolean. Missing in-card buttons open the listing rather than claiming a click. Broken checkbox flows fall back to an eligible in-card button. Hidden/disabled controls are excluded. Job-detail click suppression resets on SPA navigation and failed clicks remain retryable. Negative submission messages are not counted as successful applications.

The background application flow scopes its fallback tab search to newly opened tabs so it cannot pick an unrelated, previously open application page. Existing application safety and security handoffs remain in place. Live Naukri acceptance is NOT RUN; DOM fixture tests verify the reported button defect. An updated portal layout or an account-specific screening flow can still require further adjustment.

## Recurring opportunity scans

Open **Daily / Weekly / Monthly Scans**. Set target roles, locations, threshold and device-local time, save and enable. Use Scan now for immediate results. Scans combine saved unsubmitted workspace jobs with Remotive and Arbeitnow listings and use saved resume/profile skills. Top five results include fit, requirements, gaps and source links. Duplicate and previously surfaced links are suppressed. Feed failures are recorded separately from empty results; saved jobs remain usable offline. Disabled schedules do not run. Missed scans catch up on browser restart; monthly dates clamp to the last day of shorter months.

Chrome must be running for scheduled execution. This is not a hosted 24/7 scheduler. Public feeds do not provide exhaustive Naukri/LinkedIn/India coverage. Broader search needs approved feeds or provider integrations.

## Comp Radar

Employer and role filtering is applied to live feeds and stored salary evidence. Salary records must explicitly identify INR/lakh/LPA; foreign currency values are not guessed into INR. Samples are deduplicated. Compensation displays observed posted-range midpoints, sample counts and quantiles, without inventing experience bands, base salary, bonus or equity. Unknown company facts are marked unknown. Empty evidence yields an empty state, not generated jobs or salary estimates. Employer identity and stale listings still require review.

## Checkout implementation status

The billing page now propagates backend errors, displays provider configuration separately from live testing, opens allowlisted checkout URLs and can check a payment session. Session prices come from server-published active plans, not client input. Sessions are authenticated and owned by the user; the database prevents concurrent active sessions for the same user/provider/plan. Only provider-side amount, currency and reference matches mark supported sessions paid.

Do not enable sales until entitlement provisioning, cancellation/refund handling and acceptance tests are complete. User-entered UPI IDs and redirect pages never confirm payment. Arbitrary VPA payments are not automatically verified.

## Backend deployment

Apply migration 006 after existing migrations. Deploy payment-provider-api, commerce-checkout and payment-return, retaining the existing billing functions. commerce-checkout and payment-return have gateway JWT verification disabled in config.toml; the checkout page itself verifies a one-hour signed session token. payment-provider-api requires user authentication. Store all merchant keys only as server secrets.

For additional adapters, set COMMERCE_CHECKOUT_ENABLED=true only after the lifecycle is ready, populate credentials listed in payment-provider-api, and enable an explicit plan/provider mapping. CHECKOUT_SESSION_SECRET must have at least 32 characters for Braintree/Cashfree signed pages. Braintree requires BRAINTREE_MERCHANT_ACCOUNT_ID matching the plan currency. Cashfree uses the account phone field; validate it through your account onboarding. Shopify requires a myshopify.com merchant domain and mapped ProductVariant ID. Checkout.com and Shopify remain blocked regardless of credentials until their verification adapter is completed.

## 2.9.0.1 visibility and scan repair

Resume Analysis and Scheduled Scans now mount directly in the dashboard sidebar. The dashboard header no longer covers the workspace tool strip. Scan now uses current form values without requiring Save schedule first. Default target roles appear before the background response, and an empty profile roles array no longer empties the required roles field. Scan requests use runtime messages that wake the worker instead of a persistent port; the general background handler explicitly yields these messages to the scheduler. Errors explain how to reload the installed extension.

Additional tests exercise the shipped background bundle with its encryption wrapper and both message listeners, manual scan without a saved schedule, scan UI form submission and sidebar links. All 31 cases pass. No live browser or Naukri acceptance has been performed.
